## Context

排序核心 `computeNewOrder` 输出的结构是"歌手块序列"：每位歌手（按首次出现顺序）名下挂若干专辑，专辑内曲目按 album tracks 顺序。确认环节已有"保存新顺序文件"选项的循环 select 模式，新增选项可复用该模式。歌手块的归属判定（专辑归属艺人 = 专辑内第一首歌的 `artists[0]`，无专辑歌归 `__unknown__`）已存在于 `sort.js` 的分组逻辑中。

约束：不持久化（会话级）；仅交互向导；块内顺序不可变；提交路径复用现有 submitReorder + writeBackup。

## Goals / Non-Goals

**Goals:**

- 确认环节可进入歌手调整界面，移动式微调（置顶/上移/下移/置底），循环操作。
- 调整只重排块间顺序，块内（专辑、曲目）零变化。
- 调整后预览/位置变动刷新，走既有提交/备份/回滚。

**Non-Goals:**

- 不做拖拽式排序（clack 无此组件，方向键移动式已够用）。
- 不做跨歌手拆块/合并（违反"专辑优先"语义）。
- 不做 CLI 参数形式与持久化（用户已确认不需要）。
- 不做"调整专辑顺序"（同构功能，等有需求再说，函数设计上预留复用可能）。

## Decisions

### D1: 块的表示——从计算结果反推，而非重跑分组

调整界面需要"歌手块列表"。两种来源：

- (a) 重跑 `computeNewOrder` 的分组逻辑提取块序列；
- (b) 对 `computeNewOrder` 的**输出**（newTracks）做一次线性扫描：连续同归属歌手的曲目段即一个块。

选 **(b)**：输出本身已按"歌手块"排列（这正是排序规则的产物），线性扫描 O(n) 且天然与实际提交顺序一致——预览所见即所得，杜绝"分组逻辑与输出不一致"的风险。扫描时用与 `sort.js` 相同的 `artistKey(firstArtist(track))` 判定归属（`__unknown__` 也是合法块）。

### D2: 重排函数——纯函数 `reorderByArtistBlocks(tracks, artistOrder)`

`src/sort.js` 新增纯函数：输入任意顺序的 tracks + 目标歌手 key 顺序，输出按该顺序拼接的块。实现：先按 D1 扫描分块（Map: artistKey → 块），再按 artistOrder 顺序输出，未出现在 artistOrder 中的块保持原相对顺序追加末尾（容错：调用方漏传时不丢歌）。单测友好（无 IO），向导与未来可能的 CLI 复用同一函数。

### D3: 交互——两层循环 select

```
确认环节 select 新增: 🎚️ 调整歌手顺序
  └─ 调整界面(循环):
       select 歌手(label: 名字 + 歌曲数,当前顺序即列表顺序)
         └─ select 操作: ⬆️ 上移 / ⬇️ 下移 / ⏫ 置顶 / ⏬ 置底 / ✅ 完成 / ↩️ 放弃
       操作后回到歌手选择(列表已更新);完成/放弃回到确认环节
```

- 完成后用 D2 函数重排 newTracks，刷新预览 note 与位置变动统计。
- 放弃：恢复进入调整前的 newTracks 快照（深拷贝数组引用即可，块对象不可变）。
- 取消（Ctrl+C/ESC）走既有 `guard` → bail 路径，不提交。
- 歌手名显示用块内第一首歌的 `artists[0].name`；`__unknown__` 块显示"(无歌手信息)"。

### D4: 备份语义——备份始终是"拉取时的云端原序"

现有提交路径先 `writeBackup(playlist.id, tracks)`（tracks = 拉取的原序）再提交 newTracks。调整只改 newTracks，不动 tracks，因此备份语义自动正确（记录调整前的云端状态，回滚即恢复到本次操作前）。无需额外改动，spec 场景"调整后提交"由此满足。

### D5: 位置变动统计的口径

`previewLines` 的 moved 统计基于"原序 vs 新序"逐位对比。调整后 newTracks 变化，统计自动刷新，无需特判。

## Risks / Trade-offs

- [块识别与排序规则漂移] → D1 用输出反推而非重跑分组，扫描用的 artistKey 与 sort.js 同源（从 sort.js 导入），单一事实源。
- [歌手很多时 select 列表长] → clack select 自带滚动；label 里带歌曲数辅助定位。几十位歌手可用，上百位体验一般——接受（歌单场景罕见）。
- [调整后用户又"换一个歌单"] → 换歌单会重走拉取+计算，调整自然丢弃，无需清理（会话级语义天然成立）。
- [深拷贝成本] → 块内 track 对象只读共享，快照只需拷贝块数组（浅拷贝），O(块数)。

## Migration Plan

纯新增：`sort.js` 加纯函数、`interactive.js` 确认环节加选项。无数据迁移、无接口变化。回滚 = git revert。
